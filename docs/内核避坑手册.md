# WinDOS 内核避坑手册

> 这份文档的目的：**下次遇到同样的现象，不用重新研究。**
> 每条格式统一：**现象（日志/屏幕长什么样）→ 根因 → 改哪几行 → 验收判据**。
> 更详细的背景留在 `hermes` 技能 `windos-uefi/references/` 下（本文件是"出问题时的第一张表"）。

适用：UEFI 64 位 WinDOS（`src/main.rs` 引导器 + `kernel/` C++ 内核）。
历史 BIOS 版本（32 位、软盘引导）在 <https://github.com/boonxiong2/WinDOS-Legacy>。

## 0. 排查方法论（比任何具体结论都值钱）

1. **先探针，后结论**。别猜：写 3 行探针打印寄存器/签名/状态位，看结果再动手。
   *反例*：曾经连续十几轮"猜 QEMU IDE 有问题"，真凶却是 `io.h` 少了个 `volatile`（见 §5.1）。
2. **写已知值再读回**：验证任何"寄存器/端口能不能用"——`out8(0x173,0x5A); in8(0x173)` 期望 `5A`。两行代码自证，不需要懂硬件。
3. **日志必须分级**：`[KERNEL/INFO]`、`[KERNEL/CRITICAL]`、`[UEFI/INFO]`、`[UEFI/CRITICAL]`。禁止 `K1/K2` 式临时检查点。
4. **一次只改一处**，每处都留一条能验的日志。
5. **崩溃现场三件套**：串口日志（停在哪个 `[xx]` 之间）+ `info registers`（`CPL`/`CS`/`SS`/`CR2`）+ 屏上最后画面（`screendump`）。
6. **单 QEMU 实例**；`-no-reboot` 让三重故障直接退出而不是静默重启掩盖现场。
7. **自动输入用 `sendkey`**（小写；`sendkey ret` = 回车），别手点。
8. **视觉验证不能自称通过**——只有人能看屏幕说"OK 了"。

## 1. 引导链（UEFI）

### 1.1 表偏移：全都要按规范值，别照抄"网上经验"

`EFI_SYSTEM_TABLE`：`RuntimeServices @0x58`、`BootServices @0x60`（**这两个就是规范值**，不是 OVMF 特例）。

`EFI_BOOT_SERVICES`（表头 24 字节 + 中间有一个 `VOID *Reserved`，漏掉就整体错位）：

| 偏移 | 函数 | 偏移 | 函数 |
|---|---|---|---|
| 0x28 (40) | AllocatePages | 0x98 (152) | HandleProtocol |
| 0x38 (56) | GetMemoryMap | 0xA0 (160) | *Reserved* |
| 0x40 (64) | AllocatePool | 0xE8 (232) | ExitBootServices |
| 0x68 (104) | SignalEvent | 0x140 (320) | LocateProtocol |
| | | 0x168 (360) | SetMem |

**权威对照源**：TianoCore `MdeModulePkg/Core/Dxe/DxeMain/DxeMain.c` 里的 `mBootServices` 初始化表——
**每个条目都带 `// 函数名` 注释**，逐行数就能核对。

- **现象**：启动即黑屏 + QEMU 直接退出（三重故障）。
- **根因**：偏移写错会调用到**功能完全不同的函数**。真踩过的错：`360` 当 GetMemoryMap → 实际调了 **`SetMem`**，
  参数错位成 `SetMem(Buffer=NULL, Size=&map_sz(栈地址, 几百 MB), Value=…)` → 从地址 0 开始涂掉几百 MB 内存
  （内核镜像、memdisk 缓冲、BootInfo、页表、**正在用的栈**全没了）→ 跳内核即三重故障。
- **修法**：偏移改成 `56 / 64 / 232`；顺手核对 `AllocatePages=40`、`LocateProtocol=320` 都对（这两个一直是对的，
  能证伪"整张表读歪了"这种误判）。
- **判据**：`[UEFI/INFO] EBS OK`（= 返回 0/EFI_SUCCESS）。

### 1.2 ExitBootServices：ImageHandle 要真，MapKey 才是会咬人的那个

- **现象**：`ebs ret=0x8000000000000002`（`EFI_INVALID_PARAMETER`），或忽略返回值硬跳 → 随机崩。
- **根因**：
  - `ImageHandle` 必须是**调用映像自己的句柄**（`efi_main` 的第一个参数 `rcx`）。我们的入口是 `#[unsafe(naked)]`
    手动 prologue，**只存 `rdx`(SystemTable) 就会拿不到 ImageHandle** → 只能被迫传 SystemTable。
  - `MapKey` 是内存图指纹：**取图之后任何一次分配都会让它作废**，EBS 直接拒收。
  - ⚠️ 但别把"不传真句柄一定挂"当诊断依据：**EDK2/OVMF 的 `CoreExitBootServices` 压根不校验 ImageHandle**
    （只做三件事：发 `BeforeExitBootServices` 事件 → `gTimer->SetTimerPeriod(0)` → `CoreTerminateMemoryMap(MapKey)`）。
    规范要求传真句柄，只是因为别的固件可能校验。
- **修法**（`src/main.rs`）：
  1. `naked_asm!` 里除了 `mov [rax], rdx` 再补 `mov [rax], rcx`（存到全局 `IH`）；
  2. 所有分配（memdisk 缓冲 → 内核 16MB → BootInfo）**全部排在取图之前**；
  3. `GetMemoryMap` 探大小 → `AllocatePages` 分配缓冲 → **再取一次**拿真 key → `ExitBootServices(ih, map_key)`；
  4. **有界重试（8 次）**，失败就重新取图（`loop { if ebs()==0 break }` 在 key 失效时是死循环）；
  5. EBS 成功后 **`cli`**。
- **为什么必须 `cli`**：EBS 拆掉的是固件**定时器**，固件 **IDT 不会被重置**。内核在装上自己的 IDT/PIC 之前有一段
  长循环（本项目是填满 4MB 显存），这期间来一个中断就落进固件处理程序 → 用我们的 GDT 执行固件代码 → 三重故障。
- **判据**：`map sz=0x1860 / desc sz=0x30 / map key=0x7d9 / EBS OK`。

### 1.3 问 UEFI"我从哪块盘来"（别猜盘）

- **现象（多盘机器）**：读不到 `memdisk.img`，或者更阴——读到**另一个卷里的同名旧文件**。
- **根因**：用 `LocateProtocol(SimpleFileSystem)` 拿到的是**"任意一个"**文件系统实例。
- **修法**：`HandleProtocol(ih, LoadedImage_GUID, &li)` → `li->DeviceHandle`（`@24`）→
  - `HandleProtocol(devh, SimpleFileSystem_GUID, &fs)` → **一定是自己那个卷**；
  - `HandleProtocol(devh, DevicePath_GUID, &dp)` → 解析出**控制器类型 / PCI 位置 / 分區起点**。
- **DevicePath 节点**（`Type(1) SubType(1) Length(2) Data…`，`Length==0` 或 `Type==0x7F` 结束）：

| Type/SubType | 数据 | 取什么 |
|---|---|---|
| Hardware 0x01 / ACPI 0x02 | HID(4) UID(4) | **UID = PCI 总线号** |
| Hardware 0x01 / PCI 0x01 | Func(1) Dev(1) | **dev/func** |
| Messaging 0x03（子类型见下表） | — | **控制器类型**（ATAPI 节点还带 Primary/Secondary、Master/Slave） |
| Media 0x04 / HardDrive 0x01 | PartNum(4) **PartStart(8)@+8** **PartSize(8)@+16** | **分区起始 LBA + 扇区数** |

**Messaging 子类型必须查 EDK2 `MdePkg/Include/Protocol/DevicePath.h`，别照字面猜**
（我们曾照猜写成 0x10=SATA / 0x12=NVMe，结果 SATA 盘被报成 NVMe）：

| 子类型 | 含义 | | 子类型 | 含义 |
|---|---|---|---|---|
| 0x01 | ATAPI（传统 IDE） | | 0x12 | **SATA (AHCI)** |
| 0x05 | USB | | 0x17 | **NVMe Namespace** |
| 0x0f | USB Class | | 0x10 | USB WWID（**不是 SATA**） |

- **症状**：日志里 `ctrl kind` 与 DevicePath 文本不符（`Sata(...)` 却报 kind=3）。
- **判据**：q35 + SATA 盘 → `ctrl kind=0x2`；默认 IDE 配置 → `ctrl kind=0x1`。

- ⚠️ **易错**：`part_lba` 是"**装着这个文件的物理分区**"（QEMU 实测 = 63），**不是**镜像文件内部那个 MBR 分区（= 128）。
- **判据**：引导器打 `ctrl kind/pci addr/part lba/ch/dv`，内核打出**同一组值**（证明交接成功）。

### 1.35 选显示模式：必须自己 `SetMode`，别指望固件听你的

- **现象**：QEMU 传 `-device VGA,xres=1920,yres=1080` 也没用，OVMF 依然给 800x600。
- **根因**：GOP 只会用固件选定的**当前模式**；QEMU 的 xres/yres 只是 EDID 提示，固件可以无视。真机同理（默认模式不可控）。
- **修法**（引导器，`src/main.rs`）：拿 `SetMode @8`，用 `QueryMode @0` 遍历 `Mode->MaxMode` 个模式，
  找到**恰好**目标尺寸的那个再 `SetMode`；**找不到就保持原模式**（不改也能跑）。
  `Mode` 结构：`MaxMode @0`、`Mode @4`、`Info @8`、`SizeOfInfo @16`、`FrameBufferBase @24`；
  `SetMode` 成功后固件**就地更新**该结构（Info 指针/帧缓冲基址都可能变）→ 必须重新读一次尺寸和 `fb`。
- ⚠️ **只接受"恰好等于"目标尺寸，绝不选更大的**：内核的 `lm_map[1920*1080]` / `back_buf[1920*1080]`
  是按 FHD 开的，选到 4K(3840x2160) 会越界写约 25MB。这条规则本身就是道护栏。
- **判据**：`max mode=0x1e` → `set mode idx=0x16` → `set mode ret=0x0` → `final hr=0x780`、`final vr=0x438`，
  `screendump` 出来就是 1920x1080。
- **代价提醒**：像素量 ×4（全屏 8.3MB）→ 全屏刷新变慢，所以"少画"（裁剪 + 区域刷新）从可选变成必需。

### 1.4 从 ExFAT 读内核（`exfat_find_core`）

- 根目录项：`0x81` 文件 + `0x85` 流扩展（首簇 `@+16`、数据长度 `@+24`）+ 名字条目 `0xC0|n`；
  跳过判断用 **`nt & 0xC0 == 0xC0`**（`nt & 0x40 == 0` 是错的，会跳过所有文件名）。
- **已知局限（真实短板，未修）**：`fat_off` 解析了但**没使用**（编译器一直在警告 `unused variable: fat_off`），
  数据是按"首簇 + 长度"**连续读**的 → **KERNEL.BIN 一旦跨不连续簇就会读错**。
  目前镜���是我们自己生成的、必然连续，所以能跑。修法：沿 FAT 表跟簇链（`fat_off` 就在手边）。
- 名字条目**只读了第一段**（`off+64`）→ 超过 15 字符的名字认不出（`KERNEL.BIN` = 10 字符，未受影响）。
- 镜像上限：引导器缓冲 `mb_total = 0x40000`（256KB）→ `tools/mkmemdisk.py` 里带护栏，
  超了会明确报错并提示改哪个常量。

## 2. 内核早期（顺序 + clang -O2 陷阱）

### 2.1 `_start` 的正确顺序（这个顺序错了必翻车）

```
cli → UMIP(先 CPUID 门控再写 CR4) → 记 CR0/CR3/CR4 → 清 BSS → 装 GDT → 翻页表 US 位
    → 设 LSTAR(syscall 入口) → 初始化显示/图层/登录窗 → 装 IDT/PIC/PIT → sti
```

- **`sti` 必须在 TSS.RSP0 设置之后**：否则中断触发时切到未设置的 RSP0（垃圾栈）。
- **改页表前要清 `CR0.WP`**（否则写只读的页表页本身 #PF），改完恢复。
- **改完必须 `mov cr3` + `invlpg` 刷 TLB**，否则 Ring3 还走旧的 `US=0` 表项。

### 2.2 "用户区上界"必须按 `_bss_end` 推导，禁止写死

- **现象**：登录进 Ring3 后立刻崩；或 `syscall` 报指针越界。
- **根因（两处同一个病）**：
  1. 页表 US 位只翻了前 8MB（`pdt[0..3] |= 4`）——而 `.bss` 已 10.6MB，**用户栈落在 10.8MB**
     → Ring3 第一条 `push` 就 `#PF`，**errcode `7 = P|W|U`**（U 位 = 没给用户权限）；
  2. syscall 指针校验写死 `0x800000` → `.bss` 涨过 8MB 后会把**合法用户指针全判越界**
     （现象：`[KERNEL/USER_API/EXCPTION] Pointer DIDN'T in user mem area`）。
- **修法**：
  ```c
  extern "C" u8 _bss_end;
  u64 be; __asm__ volatile("lea %1, %0" : "=r"(be) : "m"(_bss_end));
  for (u64 i = 0; i <= (be >> 21); i++) if (pdt[i] & 1) pdt[i] |= 0x4;   /* 只翻已存在的 PDE */
  u64 lim = (be + 0x1FFFFF) & ~0x1FFFFFull;                              /* 指针校验上界 */
  ```
- **判据**：`[KERNEL] bss … sz=00A73480` → `US bits set` → Ring3 里能跑不崩。

### 2.3 clang -O2 陷阱清单（每条都真实踩过）

| 现象 | 根因 | 修法 |
|---|---|---|
| 轮询状态位**永远不变**、读同一端口总返回同一个值 | **端口读 asm 没有 `volatile`**（有输出操作数 → 被当纯函数 CSE/提出循环） | 见 §5.1，全部 `v[...]`
| 中断门地址 = 垃圾（`gate20=0x3BE6C37F`），中断不触发 | `KERN_BASE + h` 内联时 `rax` 被复用 | `volatile u64 KB = KERN_BASE;` 强制重载 |
| 阴影循环死循环 / `E06` | 循环里用**三元表达式** | ���显式 `if/else`；必要时 `#pragma clang loop unroll(disable)` |
| `continue` 后计数器不递增 → 死循环 | 复杂 `if` + `continue` 被优化 | 改成 `if` 包住整个循环体 |
| `if` 判断寄存器值被优化掉 | **register-asm 变量**是 UB | 用显式 `movq %rax, %0` 读 |
| 刷新背景时 #PF（`CR2` 固定、多处 RIP） | 内联后基址寄存器被复用成调用点垃圾值 | 背景写用 `volatile u32 *v = ctl->vram;` 强制每次重载 |

### 2.4 崩溃处理程序（死屏）自身必须 crash-safe

- **现象**：崩了但看不到现场；或者递归到栈耗尽；或者死屏上什么也没有。
- **根因**：① `ds()` 信任 `g_fb/g_stride/disp_w()/disp_h()`——**它们就在 .bss 里紧挨着大缓冲，往往正是被踩坏的那批**；
  ② 没有防重入 → 崩 → `ds()` → 又崩 → 递归，把真正的现场盖掉。
- **修法**：`static volatile int entered`（进了就 `cli; hlt` 死等）+ 显存指针/几何合法性检查
  （规范地址 + 4 字节对齐 + 宽高/步幅范围），**不可信时只打串口不画屏**。
- **判据**：`[KERNEL/CRITICAL/INFO]BSOD DREW` 或 `BSOD SKIPPED (display state unusable)`——两者都是"正常工作"。

## 2.5 绘制基元必须带裁剪 + 哨兵自检（`kernel/sys/draw.h`）

- **现象**：崩在**完全无关**的地方（改一处坐标、另一处变量被踩坏）。
- **根因**：`fill_rect` / `put_char` 没有任何边界检查，而窗口缓冲是 `.bss` 里的静态数组
  → 坐标一旦算错就写到**别的全局变量**上（`back_buf` 那两次事故是同一类）。
- **修法**：`sys/draw.h` 提供带裁剪的基元：`clip_rect` / `fill_rect_c` / `blit_c`（带透明色）/
  `put_char_c` / `put_str_c` / `blend_alpha`。**不替代图层系统**（`sheet_refreshsub/refreshmap`
  早就有屏幕裁剪），只给"直接往缓冲画"的地方兜底。
- **哨兵自检**（比"看它崩不崩"可靠）：在缓冲**前后各放一段魔数**（`0xDEADBEEF`），
  故意用界外坐标调各个基元，最后检查魔数是否被改。
  ⚠️ 哨兵必须放在缓冲**之外**——本项目第一次写就写成 `PAD + N*N - 1 - i`（与缓冲尾重叠）→ 自己误报 FAIL。
- **判据**：`[KERNEL/INFO] [DRAW] selftest PASS (r=0)`；界内必须画上、界外必须一个字节都不碰。

## 9. NVMe 驱动（PCIe / MMIO / 64 位 BAR）

> 2026-10 实测：`-device nvme,serial=WINDBG01,drive=nvm`。
> 全链路判据（一条不断）：
> `init=0 CSTS=1` → `IDENTIFY(ctrl)=0 SN="WINDBG01" MN="QEMU NVMe Ctrl" NS=256`
> → `create_io_q=0` → `WRITE lba0=0` → `READ lba0=0 data="HI FROM NVME"`

### 9.1 八步顺序（少一步就卡在后面）

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 | PCI 枚举找控制器（class 01/08，QEMU 兜底 vid 1B36） | `dev4 vid=1B36 cls=1/8` |
| 2 | 读 BAR0/BAR1 拼 64 位 MMIO 基址 | `find=0x800000000` |
| 3 | 把 BAR0 映射进页表（PDPT[32] + 新 PDT 页） | 不映射时读回 `0xFFFFFFFF` |
| 4 | 读 CAP（64 位） | `CAP=0x004008200F0107FF` |
| 5 | 写 AQA / ASQ / ACQ | `AQA=003F003F` |
| 6 | 写 CC（EN=1）→ 等 CSTS.RDY | `init=0 CSTS=1` |
| 7 | Admin 队列发 IDENTIFY | `IDENTIFY(ctrl)=0` |
| 8 | 建 I/O 队列(qid=1) → READ/WRITE | `READ ... data="..."` 一致 |

### 9.2 ★ 最容易错的一条：CC 的 IOSQES / IOCQES 位

- **现象**：`CSTS.RDY=1`（控制器明明起来了），但 `IDENTIFY` **永远超时 `-2`**。
- **根因**：CC 写成 `(6 << 8) | (4 << 4) | 1 = 0x00000641` —— 那是**错的位表**。
  规范里 **IOSQES 在 bits 19:16**、**IOCQES 在 bits 23:20**（不是 8-11 / 4-7）。
  写错后 `IOSQES = IOCQES = 0` → 控制器按 `2^0 = 1 字节`读 SQE → **命令永远收不全** → 不产生 CQE → 超时。
- **正解**：`CC = 0x00460001`（EN=1, CSS=0 即 NVMe 命令集, MPS=0 即 4KB 页, IOSQES=6 即 64B, IOCQES=4 即 16B）。
- **判据**：`IDENTIFY(ctrl)=0`（从 `-2` 变 `0`）。

### 9.3 门铃偏移通式

```
SQ(qid) tail = 0x1000 + (2*qid)     * 4
CQ(qid) head = 0x1000 + (2*qid + 1) * 4
qid=0 (Admin) → 0x1000 / 0x1004      qid=1 (I/O) → 0x1008 / 0x100C
```
（`CAP.DSTRD != 0` 时步长 = `4 << DSTRD`，本机 DSTRD=0。）

### 9.4 CQE 相位位（不是 bit1）

- 相位位在 **CQE dword3 的 bit16**；**初值 1**；`head` 绕回 0 时 `^= 1`。
- 读到一个 CQE 后**必须写 CQ head 门铃**告诉控制器"我读走了"。
- `status code = (dw3>>17)&0xFF`、`status type = (dw3>>25)&0x7`；两者**联合**判定，只看 sc 会把某些错误当成功。

### 9.5 队列内存必须 4KB 对齐 + 物理连续

- 用 `desk/page.h` 的 `page_alloc(1)`（identity map：虚拟地址 == 物理地址，可直接交硬件）。
- **不能用栈数组**（无法保证对齐）、**不能用 `kmalloc`**（slab 最大 1KB）。
- Admin：SQ 64 项×64B = 4KB、CQ 64 项×16B = 1KB（1 页够）。I/O 同规格。

### 9.6 SQE / CQE 与 CID

- **SQE = 64B**（16 个 u32）、**CQE = 16B**（4 个 u32）—— 别把两者搞混。
- **CID 写在 dw0 的 bits31:16**；**CID 从 1 起**（0 保留：QEMU 在 MSI-X 边界会补投 CID=0 的幽灵 CQE）。
- 写完 SQE **必须内存屏障**（`__asm__ volatile("" ::: "memory")`）**再敲门铃**，否则编译器可能把门铃提到 SQE 写之前。

### 9.7 MMIO 映射要点

- 32GB 处：`pdptt[32] = 新PDT页 | 0x03`；`nvme_pdt[0] = 0x800000000 | 0x83`（bit7=PS 2MB 大页）。
- **US 必须为 0**：用户态要是能写 `CC.EN`，就能直接关盘 / 用 DMA 读内核内存。
- **未映射时读回 `0xFFFFFFFF`** —— 它的含义是"地址访问不通"，**不是**"设备不存在"。

### 9.8 读写参数（踩过的坑）

- 命令：**READ = 0x02 / WRITE = 0x01**；`NSID` 用 **1**（`NS=256` 是**命名空间数量**，不是 ID）。
- `dw10` / `dw11` = SLBA **低 / 高 32 位**；`dw12` 低 16 位 = **NLB - 1**（不是 NLB）。
- `dw6` / `dw7` = PRP1（64 位物理地址）；单页 4KB = 8 个 512B 块。
- 建队列：Create I/O CQ = opcode **0x05**（dw11: PC=1）；Create I/O SQ = opcode **0x01**（dw11: CQID<<16 | PC=1）。


## 附录：AI 性能审查（Copilot 输出）核实记录

> 目的：把外部 AI 给出的性能审查逐条和真实代码比对，记录哪些结论成立、哪些是误读、哪些是设计权衡。

1) 内层乘法 / stride 重复计算 — 判定：**误读**。
   - Copilot 把 `u32 *row = fb + (u32)(y + dy) * stride + (u32)x;` 当作在内层重复计算。
   - 事实：乘法在外层 `for (dy = 0; dy < h; dy++)` 里计算，每行一次。编译器会把不变表达式外提或该写法已是最优形态。
   - 结论：不需要改动。

2) 内层边界检查冗余 — 判定：**误判危险**（不要删）。
   - Copilot 建议移除 `vx >= 0` / `vx < xsize` 等检查以加速。
   - 事实：窗口可以拖到屏幕外，`sht->vx0` 可能为负，`bx` 是图层内坐标，必须在像素级检查屏幕坐标，否则会写越界。
   - 结论：保持现状；若要优化，改成分支预测友好的两段处理（完全在屏内的快速路径 + 边缘路径）并加回 safety checks。

3) 阴影合成逐像素算术 — 判定：**设计取舍**。
   - Copilot 建议用查表 / SIMD 来替代逐像素减法。
   - 事实：阴影采用“合成减”设计，每像素做三次分量运算与 clamp，这是显式且可预测的且符合当前实现意图。
   - 结论：可优化（256-entry 查表或 SIMD），但不是紧急 bug；先保留可读正确实现，再视性能需求逐步替换。

4) 全屏刷新被误读为每帧操作 — 判定：**误读**。
   - Copilot 强调 `shtctl_refresh_all()` 写 2M 像素、优先级高。
   - 事实：此函数在启动/重绘场景调用；正常运行采用脏矩形/局部刷新（`sheet_refresh*`）和中断驱动事件，不会每帧 60fps 全屏刷。
   - 结论：无需把全屏刷作为主要优化目标，但仍应关注大变更路径的成本。

5) ExFAT 目录遍历 — 判定：**成立但影响小**。
   - Copilot 指出引导器手写遍历目录表的代码，属于一次性启动成本。
   - 结论：正确，但只在引导时运行，优先级低。

6) `#pragma clang loop unroll(disable)` — 判定：**有效但是正确性对性能的权衡**。
   - Copilot 指出这阻止向量化/编译器优化。
   - 事实：这是为避免 clang -O2 在特定循环产生错误展开（导致死循环 / E06）而采取的权宜措施。
   - 结论：这是技术债，长远可通过重写循环逻辑或显式保证步长消除该 bug，再移除 pragma。
